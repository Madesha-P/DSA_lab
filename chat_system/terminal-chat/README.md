# Terminal Chat (Static GitHub Pages + Supabase)

This project is a **fully static anonymous terminal chat**.

- Frontend: HTML, CSS, Vanilla JS
- Hosting: GitHub Pages
- Database + Realtime: Supabase
- No login, no signup, no username, no profile

---

## 1) Architecture

```text
USER
  ↓
GitHub Pages (static files)
  ↓
index.html + script.js
  ↓
Supabase JS client (public anon key)
  ├─ PostgreSQL `messages` table
  └─ Realtime subscriptions (INSERT + DELETE)
```

Send flow:
1. User types message
2. JS validates and trims message
3. JS inserts message into Supabase
4. DB stores row
5. Realtime INSERT broadcasts to all clients
6. Terminal renders line safely with `textContent`

Delete flow:
1. Admin runs `DELETE FROM messages;` in Supabase
2. Rows are removed from PostgreSQL
3. Realtime DELETE events arrive to connected clients
4. Displayed rows are removed
5. Refresh loads empty state from DB

## 2) Supabase Setup (beginner-friendly)

### Step 1: Create account
1. Open `https://supabase.com`
2. Click **Start your project**
3. Sign up (GitHub/Google/email)
4. Expected: you can access Supabase dashboard

### Step 2: Create a project
1. In dashboard, click **New project**
2. Choose organization
3. Enter project name (example: `terminal-chat`)
4. Set a strong DB password
5. Select region
6. Click **Create new project**
7. Expected: project dashboard opens

### Step 3: Open SQL Editor
1. Left menu → **SQL Editor**
2. Click **New query**

### Step 4: Create `messages` table
1. Paste SQL from section **3) SQL** below
2. Click **Run**
3. Expected: query succeeds
4. Verify in **Table Editor**: `messages` table exists

### Step 5: Enable RLS
1. Left menu → **Table Editor** → `messages`
2. Open **Policies** tab
3. Verify RLS is enabled (or run SQL in section 3)

### Step 6: Create SELECT policy
1. In SQL Editor, run policy SQL from section 3
2. Expected: policy created
3. Verify in Policies tab: `public_can_select_messages`

### Step 7: Create INSERT policy
1. In SQL Editor, run policy SQL from section 3
2. Expected: policy created
3. Verify in Policies tab: `public_can_insert_messages`

### Step 8: Do NOT create public UPDATE/DELETE policies
- No public `UPDATE` policy
- No public `DELETE` policy

### Step 9: Enable Realtime for table
1. Left menu → **Database** → **Replication** (or **Realtime** depending on UI)
2. Locate table `public.messages`
3. Toggle it ON for realtime replication
4. Expected: table is included in realtime publication

### Step 10: Configure DELETE events support
Run this SQL:
```sql
alter table public.messages replica identity full;
```
This ensures delete payloads include old row data reliably.

### Step 11: Find project URL
1. Left menu → **Project Settings** → **API**
2. Copy **Project URL**

### Step 12: Find public/anon key
1. On same API page
2. Copy **anon public** key (or publishable key)
3. Do **NOT** copy service_role key into frontend

### Step 13: Put values into `config.js`
Open `config.js` and set:
```js
const SUPABASE_URL = "YOUR_SUPABASE_URL";
const SUPABASE_ANON_KEY = "YOUR_SUPABASE_ANON_KEY";
```

## 3) SQL (copy-paste ready)

```sql
-- 1) Table
create table if not exists public.messages (
    id bigint generated by default as identity primary key,
    message text not null,
    created_at timestamptz not null default now()
);

-- 2) RLS
alter table public.messages enable row level security;

-- 3) Policies
create policy public_can_select_messages
on public.messages
for select
using (true);

create policy public_can_insert_messages
on public.messages
for insert
to anon, authenticated
with check (
  char_length(trim(message)) > 0
  and char_length(message) <= 500
);

-- 4) Realtime delete payload support
alter table public.messages replica identity full;
```

Important:
- Do not create `UPDATE` policy.
- Do not create `DELETE` policy.

## 7) Security

### RLS
RLS protects table operations even though browser key is public.
Policies allow only what you define.

### Public key vs service-role key
- `anon` key: safe for browser use **with strict RLS**
- `service_role` key: full bypass power, **never put in frontend files**

### XSS protection
All messages render with `textContent`, never with `innerHTML`.
So `<script>`, `<img onerror>`, `<b>` are displayed as text only.

### Message validation
- trim whitespace
- reject empty
- max 500 chars
- DB policy also enforces non-empty and <=500

### Rate limiting
- Client-side cooldown (~1.2s/message) is added for spam reduction UX.
- Client-side checks are bypassable.
- For stronger protection, add server-side controls with Supabase Edge Functions or RPC/database rate-limit logic.

### Why public client cannot delete
Because there is **no DELETE policy** for `anon/authenticated` roles.
So browser clients can SELECT/INSERT only.

---

## 8) How Database Clearing Works

When admin runs:

```sql
DELETE FROM public.messages;
```

- PostgreSQL permanently deletes rows.
- Realtime DELETE events are pushed to connected clients.
- `script.js` removes deleted message lines from the terminal.
- On refresh, app reloads from DB (now empty), so deleted messages never return.
- `/clear` never touches the database.

## Final: How to connect "backend" to Supabase in this static app

In this architecture, Supabase **is** the backend.

1. Create table + RLS + policies in Supabase (SQL section above).
2. Copy Project URL + anon key from Supabase API settings.
3. Put them in `config.js`.
4. `script.js` calls:
   - `createClient(SUPABASE_URL, SUPABASE_ANON_KEY)`
   - `.from('messages').select(...)`
   - `.from('messages').insert(...)`
   - `.channel(...).on('postgres_changes', ...)`
5. Deploy static files to GitHub Pages.

That is the complete frontend-to-backend connection for this anonymous terminal chat.
